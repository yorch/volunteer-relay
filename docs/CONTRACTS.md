# Current contracts and HTTP boundaries

Canonical schemas and service ports live in [`packages/contracts/src/index.ts`](../packages/contracts/src/index.ts) and the exported contract modules. The schemas marked `.strict()` reject extra fields; other endpoint input checks are implemented by their respective handlers. Wire instants use ISO timestamps with offsets; activity dates carry day or unknown precision. Evidence offsets are JavaScript UTF-16 indices, half-open `[start,end)`, against the exact preserved source revision. Attachment observations do not establish identity or duration. IDs are opaque; tenant-owned records are scoped by organization.

A verified session and current membership establish tenant context on the server. Parsing an organization ID or hiding a link does not grant authority. Owners and coordinators can submit sources, review, manage needs and read reports; volunteers can submit sources, and report-readers receive aggregate reports without private evidence. Member administration is owner-only. Repositories recheck current membership, and cross-tenant source access is concealed. System work uses its own bounded paths rather than human permissions.

## HTTP transport

The explicit authentication endpoints under `/api/auth/` cover sign-in, sign-up, sign-out, reset request/confirm, verification request/confirm, invitation acceptance, organization listing and selection. There is no general Better Auth SDK catchall. Auth JSON bodies are limited to 16 KiB. Mutating requests require the configured application origin, and session cookies and refreshed headers are passed through. Sign-up creates an account without organization membership; email verification alone does not create one. Mail must be configured for verification, reset and invitation delivery.

`GET /api/auth/invitations` (additive) lists invitations waiting for the signed-in user, returning strict `authPendingInvitationsSchema`: `{ emailVerified, invitations: [{ invitationId, organizationName, role, expiresAt }] }`. Like organization listing it is a same-origin GET with `no-store`, requires a session (401 otherwise) and is rate limited per client address. The recipient is always the verified session's own email, never a request field. An unverified email receives `{ emailVerified: false, invitations: [] }` before any lookup, so the signal discloses only the caller's own verification state. For a verified email, rows come from Better Auth's `listUserInvitations` (stored lowercased, matched case-insensitively as acceptance does) and are kept only if pending, unexpired and in a contract role; they are sorted by soonest expiry then ID and capped at `AUTH_PENDING_INVITATIONS_LIMIT` (20). Organization IDs, the inviter and the recipient email are never returned, and other recipients' invitations are never listed, so the endpoint reveals nothing about an organization to a non-recipient. The invitation ID is returned because it is the value the recipient already holds from the emailed link and is all acceptance needs; it is not authority by itself, since `POST invitations/accept` still requires the session's verified email to match the recipient, plus pending status and expiry, and Better Auth creates the membership. The zero-organization workspace panel is the only caller.

`POST /api/auth/invitations/accept` failures (additive codes in `errorCodeSchema`, statuses in `errorCodeHttpStatus`): no session is `UNAUTHENTICATED` 401. A session whose own email is unverified gets `EMAIL_NOT_VERIFIED` 403 before any invitation lookup, so it reveals only the caller's verification state. For a verified caller the lookup covers only pending invitations addressed to the session's own email: an expired one is `INVITATION_EXPIRED` 410. Everything else is `NOT_AVAILABLE` 404: an unknown ID, another recipient's invitation (expired or not), an accepted or canceled one, or a later library refusal. Those cases share one status and one fixed body that differs only in `correlationId`, so the endpoint cannot be used to probe invitation IDs or recipient emails. Messages are fixed per code; responses stay `no-store`. These codes are not emitted by product routes. Tenant-scoped product requests from a session whose email is not verified are refused with `FORBIDDEN` before any membership read (defense in depth; membership is only created for verified emails).

The `/api/product/[...path]` handler resolves the session and organization before dispatch. Its JSON successes use `{ "ok": true, "value": ... }`, generally with HTTP 200, including durable source receipts. Failures use `{ "ok": false, "error": { "code", "message", "correlationId", "retryable" } }`; product errors are sanitized. Error codes map to `UNAUTHENTICATED` 401, `FORBIDDEN` 403, `NOT_FOUND` 404, `VALIDATION` 422, `CONFLICT` 409, `RATE_LIMITED` 429 and `DEPENDENCY_UNAVAILABLE` 503 (the auth-only `EMAIL_NOT_VERIFIED` 403, `INVITATION_EXPIRED` 410 and `NOT_AVAILABLE` 404 share the same `errorCodeHttpStatus` table). Unsupported methods receive 405. Product responses use `no-store`; POST requires an `Origin` matching `APP_URL`. Ordinary product JSON commands are bounded to 64 KiB. CSV reports, private attachment bytes and the signed redaction ledger are direct responses with their own content types rather than Result JSON.

Mutating (non-GET) product requests may carry the optional `x-relay-org` header (`ORGANIZATION_ASSERTION_HEADER`) with the organization ID the client believes it is acting in, so a tab showing one workspace cannot silently write into another after the session's active organization changed elsewhere. It is an assertion only, never authority: the server still resolves tenant context from the verified session and live membership. The central dispatcher checks it after session resolution and before any handler, including multipart photo/import and composed extension routes, reads a body or writes. A value that differs from the resolved organization yields 409 `CONFLICT` with a neutral message and no write; the response never names the resolved or asserted organization, and an asserted organization the user does not belong to receives the same response, so the header is not a membership oracle. A malformed value (outside `organizationAssertionSchema`, `[A-Za-z0-9_-]{1,128}`, including empty or repeated headers) yields 422 `VALIDATION`. An absent header leaves behavior unchanged, and GET requests ignore it. This is additive and does not change any schema version.

Current product paths include:

- `GET workspace` and `GET source?sourceId=...` for role-filtered workspace and authorized source evidence. Source summaries now include a bounded text preview and received instant, excluding redacted sources and rechecking current membership; volunteers receive their own summaries only. The optional batched `activities` projection carries type/date facts for staff ledger rows, with live tenant/user/role predicates. Report-reader private arrays remain empty. Staff may inspect a failed source before retrying it.
- `POST sources` for strict `WebSourceSubmission` (`schemaVersion`, `idempotencyKey`, `text`); the server derives organization, author, identity and timestamps. `POST source-photo` accepts multipart `file`, `text` and `idempotencyKey`; it validates and normalizes image bytes before storing a private attachment. Text and photo retries with a changed payload conflict.
- `POST review`, `activity`, `contribution`, `need` and `need-transition` for their canonical commands. Reviews use optimistic revision and idempotency; activity links and corrections require explicit staff decisions and reasons. An accepted urgent provisional need remains provisional until staff confirms it.
- `POST import-preview` and `import` for JSON, CSV or WhatsApp text. Imports accept bounded JSON or multipart with one `data` JSON field and repeated `files`. Explicit `photoMapping` maps external message IDs to filename arrays; absent mapping can infer the documented `photos` field from JSON/CSV rows. Images are content-validated, resized and stripped of metadata; preview errors block confirmation. See [import-photo tests](../tests/integration/import-photos/README.md) for supported reference syntax and limits.
- `GET attachments/{sourceId}/{attachmentId}` for authorized private reads; `GET reports` and `reports.csv` use the same report query and organization timezone. Report-reader access does not expose source text or individual evidence.
- Settings, members, notifications, delivery/audit/operations views, candidate lookup, retry/reprocess, Telegram linking and retention endpoints are composed in `apps/web/lib/product/production.ts`. Their handlers enforce their own current roles and input validation; retention redaction and signed ledger export require owner authority, and the ledger additionally requires its configured signing key.

The Telegram webhook is `/api/telegram/webhook`; it validates the configured webhook secret and uses server-resolved identity and organization selection. See the intake and Telegram services for payload and replay boundaries. `/api/health` and `/api/ready` are operational probes, not tenant authorization.

## Persistence, review and reporting

`SourceRepository.accept` persists source and outbox atomically. Its idempotency scope is organization, channel, channel identity and key: an identical replay returns the stored receipt and a changed payload conflicts. A receipt establishes durable intake, not an approved contribution. Original source revisions and evidence survive subsequent edits; current authority is checked again on execution.

Extraction proposals are untrusted candidates. Processing leases bind the active policy version, proposal evidence is validated, and review or the narrow validated-automation gate decides what can be recorded. Ambiguous participants, duplicate candidates, corrections, missing duration and urgent provisional needs require the appropriate review path. Cross-source links must be selected explicitly. Acknowledgment and resolution are distinct need transitions. Approved contribution minutes form the reporting ledger; unknown duration is null and pending contributions do not count as approved time.

`ProductReport` (`packages/contracts/src/reports.ts`) carries additive, optional dashboard fields described by strict `reportDashboardSchema`; clients treat an absent field as not provided, never as zero. `weekRange` (`{ from, to }`, the Monday–Sunday local week from `reportWeekRange(timezone, now)` in the organization timezone), `weekApprovedMinutes` and `weekHours` sum approved minutes on activities dated inside that week, keep the program and volunteer filters, ignore `from`/`to`, and exclude unknown-date activities; all three are null when the timezone yields no week, while a week without approved time is a known `0`. `unassignedOpenNeeds` counts open needs without an owner under the same date filter as `openNeeds`. Two fields are returned by `GET reports` only when the caller also holds `review:write` (staff) and are omitted entirely for aggregate-only report readers: `topContributors` (at most `REPORT_TOP_CONTRIBUTORS_LIMIT` = 5 `{ membershipId, approvedMinutes, approvedContributions }`, ranked by minutes, then count, then id, under the report filters), `oldestQueuedReviewAt` (instant the oldest current review queue entry was created, using the same predicate as `listQueue`; null when the queue is empty), and the volunteer hours roster `volunteers` with its paired `volunteersTruncated` boolean (both present or both absent). `volunteers` holds strict `reportVolunteerSchema` rows `{ membershipId, approvedMinutes, weekApprovedMinutes, approvedContributions, pendingContributions, pendingUnknownDuration }` for every resolved member with at least one approved or pending contribution under the same `from`/`to`/`program`/`membershipId` predicates as `ledger.approvedMinutes` (so the rows partition that total), ordered by `approvedMinutes` descending then `membershipId` (code-unit order), capped at `REPORT_VOLUNTEERS_LIMIT` = 500 with `volunteersTruncated` true when more members were in scope. Pending figures are contribution counts, never minutes; `pendingUnknownDuration` is a subset of `pendingContributions`; `weekApprovedMinutes` uses the report `weekRange` (ignoring `from`/`to`, keeping program and volunteer filters) and is null exactly when the week is unknown. Members without contributions in scope are not listed. `reports.csv` keeps its original columns in order and appends `weekFrom`, `weekTo`, `weekApprovedMinutes`, `weekHours` and `unassignedOpenNeeds`; it never contains per-member rows (including `volunteers`), queue facts or evidence identifiers, and unknown values are empty cells. Cells beginning with `=`, `+`, `-`, `@`, tab or carriage return are prefixed with an apostrophe.

Roster v2 (additive, backward compatible). `reportQuerySchema` accepts an optional `view` (`reportViewSchema`: `"summary"` | `"volunteers"`); absent means `"summary"`, so existing callers and the default `reports.csv` stay byte-identical, `GET reports` accepts and ignores it, and the echoed `query` never contains it. `GET reports.csv?view=volunteers` is staff-only (`review:write`, checked before any lookup; otherwise `FORBIDDEN`) and returns `volunteer-hours.csv`: a header `membershipId,volunteerName,approvedMinutes,approvedHours,weekApprovedMinutes,approvedContributions,pendingContributions,pendingUnknownDuration` and one row per `volunteers` roster row in roster order under the same filters and the same 500-row cap (`x-report-truncated: true|false` flags the cut). `volunteerName` is the current member's name resolved inside the server-resolved organization; a former member's name and an unknown week are empty cells, and every cell uses the same formula guard. When `GET reports` has a `membershipId` filter and the caller is staff, `volunteerDetail` (strict `reportVolunteerDetailSchema`) is added: `{ membershipId, weeks, unknownDateContributions, byActivity, byActivityTruncated }`. `weeks` holds exactly `REPORT_DETAIL_WEEKS` = 8 consecutive `{ weekStart, approvedMinutes }` organization-local Monday weeks, oldest first, ending with `weekRange` (see `reportDetailWeekStarts`); weeks without approved time are a known `0`; it keeps the program filter, ignores `from`/`to`, and is null when the week is unknown. Approved contributions on unknown-date activities never land in a week and are counted in `unknownDateContributions` (program filter, no dates). `byActivity` rows `{ activityId, kind, localDate, approvedMinutes, approvedContributions }` (activities have a kind and a nullable local date, not a name) use every report filter, are ordered by approved minutes descending then activity id, and are capped at `REPORT_DETAIL_ACTIVITIES_LIMIT` = 20 with `byActivityTruncated`; uncapped, they sum to the volunteer's approved total. Aggregate-only readers never receive `volunteerDetail`. The Summary roster's search, sort and page (`?vq=`, `?vsort=<name|approved|week|contributions|pending>-<asc|desc>`, `?vpage=`) and the "members with no contributions" toggle are client-side over the returned rows and snapshot members; they are not wire fields.

Outbox and delivery jobs tolerate replay; external provider acceptance is distinct from human acknowledgment and does not guarantee exactly-once delivery. Notification recipients are tenant-resolved and internal links remain application paths. Retention removes expired source evidence and schedules private blob erasure while preserving approved numeric ledger values. Signed current redaction ledgers are required for safe restore; see [operations](operations.md).

The ADRs document the decisions and scope at their dates. Statements in historical ADRs and task cards about deferred implementations describe those earlier phases; this page and the current source describe the integrated interfaces. Schemas alone do not prove tenant ownership, current membership, evidence fidelity, timezone semantics or provider delivery.

Settings routing rejects reserved object keys before record parsing, so an unsupported category cannot silently disappear. The UI uses named staff choices and preserves an unavailable fallback until the owner explicitly replaces or removes it; server-side role checks remain authoritative.
