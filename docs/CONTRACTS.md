# Contract baseline v1

Canonical schemas and service ports: `packages/contracts/src/index.ts`. Runtime schemas are strict and wire dates use ISO instants with offsets; local activity dates preserve day/unknown precision. Evidence identifies the proposed field it supports. Evidence offsets are JavaScript UTF-16 string indices, half-open [start,end), relative to the exact preserved source revision. Attachment observations never establish identity or duration. IDs are opaque nonempty strings, organization-scoped in storage. Context is trusted only after AuthorizationService resolution; all repository/service calls still enforce matching tenant and permission. Not-found responses conceal cross-tenant existence.

SourceRepository.accept owns one transaction for source plus outbox. Its idempotency key is unique within organization/channel identity; identical replay returns the prior receipt; a changed payload with the same key is CONFLICT. Revisions and explicit edit identity preserve evidence. A receipt means durable intake, never approved business data. HTTP adapter: POST source uses the SourceEnvelope body and server-resolved context, returns 202 Receipt; error envelope maps UNAUTHENTICATED=401, FORBIDDEN=403, NOT_FOUND=404, VALIDATION=422, CONFLICT=409, RATE_LIMITED=429, DEPENDENCY_UNAVAILABLE=503. No routes implement this yet.

Events carry stable event IDs, tenant, actor, aggregate revision and correlation ID. Outbox consumers deduplicate organization plus event ID plus handler name; external acceptance is not human acknowledgment. Review decisions use expectedRevision and idempotencyKey. Model proposals are untrusted candidates, never authorization or approved records. All unknown fields are explicit nulls or unresolved entries. Notification recipients are resolved within tenant; appPath must be an internal authenticated deep link. Delivery transport does not decide routing.

This is the frozen starter interface, not a claim that every later use case has a complete port. Need lifecycle commands, reporting queries, Telegram callbacks, upload writes, policy edits and edited review payloads require an A-owned additive contract task before consumer implementation. Agents may design proposals independently but must not create conflicting local interfaces. Schema parsing cannot validate database ownership, membership, quote fidelity, timezone semantics or policy; those checks belong to implementing services.

## First-wave authorization policy

P1-01 uses only the four contract roles. Owner/coordinator may source:submit, review:write, need:manage and report:read; volunteer may source:submit; report-reader may report:read. The last permission grants aggregate reporting, not private evidence access. Better Auth organization/member administration remains owner-only; coordinator app permissions do not imply invitation/role-management authority. Roles stored for memberships/invitations are constrained from roleSchema.options, with no silent member/admin aliases. Default-member invitation paths fail closed until explicit contract-role validation is wired before exposure.

Callers supply user IDs only from verified server sessions; authorization re-reads current membership/role on each require. Removed memberships resolve as NOT_FOUND without tenant existence disclosure; a stale, replaced or removed membership context is FORBIDDEN. Row deletion is the P1-01 revocation representation; audit integration comes with the later audit/domain slice. System actors are denied these human permissions; future worker authority needs its own bounded contract. These are agreed semantics, not a claim that B's implementation has passed acceptance.

## Second-wave bounded contracts

Additive WebSourceSubmission, ReviewDecision, ReviewOutcome and ReviewQueueEntry schemas/types are frozen for the second wave; see [ADR 0005](adr/0005-phase1-source-boundaries.md). Existing source/event/receipt and ReviewService wire shapes remain v1 and unchanged. ReviewDecision permits only accept/reject. ReviewQueueEntry.revision is the review aggregate's optimistic revision, independent of source.revision; the entry's source and proposal must share tenant, source ID and source revision. These schemas validate structure, not authorization, evidence fidelity or business completeness.

WebSourceSubmission contains schemaVersion:1, idempotencyKey and nonblank text only (20,000 UTF-16-code-unit default maximum). Future server adapters derive tenant/author/source identity/timestamps; files and client authority fields are rejected. No endpoint implements this command yet. The fixture UI must label simulated receipts and cannot claim saved data.

B/P1-02's first slice is human-authorized SourceRepository accept/get with atomic source/outbox persistence. ADR 0005 freezes the exact idempotency tuple, sequential revision/external identity rules, current-membership/own-submission evidence policy, tenant-scoped references and outbox provenance. System actors, workers, proposal persistence, ReviewService/ledger effects and corrections remain deferred. Replaying an accepted key still requires live authorization and returns the original stored receipt. Report-readers receive no private source access.

Schema-review clarification: source/attachment/outbox identities and references remain tenant-scoped even when opaque IDs collide across tenants. Preserved source revisions must survive membership row deletion, so immutable historical author references cannot restrict that deletion or cascade evidence away. Stable historical anchors do not authorize access. Preserve original envelope timestamps/values and stable attachment metadata; hash an unambiguous event identity tuple. ADR 0005 records storage/error expectations without adding shared wire types.

Review disposition clarification: a currently authorized staff replay uses the stored original receipt even after the historical author leaves; revocation of the caller still denies the operation. Historical-author existence is checked for genuinely new acceptance. Predecessor lineage is mandatory for later revisions, and storage failures must not expose raw driver details/source envelopes. Current author pointers remain same-tenant; outbox identities and future consumer dedupe are organization-scoped. See ADR 0005 and the P1-02-01 disposition.
