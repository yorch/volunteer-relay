# Native harness boundary

Codex remains the default. Existing `binary` and per-lane `model` configuration and legacy records without `harness` retain Codex semantics. No active lane is configured to Pi by this change. Optional `binaries.codex`/`binaries.pi` are absolute installed executables, never shell command strings. The supervisor still owns stdin, exclusive lane/worktree execution, four total slots, bounded logs, usage/time/run limits, lease, drain and failure pause.

## Configuration and session identity

Each lane may specify `harness: "codex" | "pi"`. Legacy `model` is Codex-only. Pi uses optional `piModel: {provider,id}`; omission is explicitly labeled an unspecified Pi saved default, not an observed model. Pi currently requires `piPermissions: "no-tools"` and a fresh `sessionEpoch`. Unknown harness, missing binary, mixed model settings and unsupported Pi permissions fail validation. Dashboard shows configured harness/model separately from recorded harness and observed provider/model.

Harness/epoch selection is startup-only. Drain/stop the existing controller and wait for all lane processes to finish before switching. Only an idle lane may switch, with a new explicit sessionEpoch; the new key retains old native records. A paused/uncertain prior run must be inspected and resolved first. Never copy an old session ID into a new harness or epoch. A legacy native session belongs to Codex; cross-harness/epoch resume fails closed. No latest-session discovery. Every new native ID is captured from the actual harness stream and Pi's session cwd must match the assigned checkout. Changing back to Codex also requires a fresh epoch. Keep runtime budgets unchanged and restart through the operator channel, never launch a duplicate.

## Installed Pi evidence and limitations

Inspected installed Pi 1.5.0 help plus its cli.md, json.md, sessions.md, security.md and models-configuration.md under the managed installation. Help initially hit the harness filesystem sandbox on Pi's own trust lock; normal approved execution succeeded. No package installation/upgrade, active harness/model/provider change or permission bypass was used.

Pi security documentation explicitly says it runs with the launching OS user's permissions, lacks per-tool approval, and project trust is not a sandbox. Therefore this initial adapter supports tool-free invocations ONLY: --no-tools, --no-extensions, --no-skills, --no-prompt-templates, --no-mcp, --no-context-files, --no-approve and --offline. The last flag disables startup network operations, not inference network access. Do not enable Pi for implementation/browser/board-tool workloads and claim parity with Codex approval/workspace isolation. A future writable Pi adapter needs a separately verified approved isolation boundary. Merely setting cwd, trusting a project, enabling read-only tools or supplying a wrapper path does not establish one.

JSON invocation uses --mode json --print and piped stdin, not Codex flags. Pi has no --output-schema/output-last-message equivalent in this adapter: the fixed prompt asks for canonical final JSON, the parser validates exact allowed state/summary keys and length, requires a completed assistant response and non-aborted agent_settled, and writes the result privately. Invalid/missing finals, changed session IDs, wrong cwd or failures pause rather than pretending success. Session capture uses Pi's session header ID; exact resume uses --session with the full captured ID in the private supervisor pi-sessions directory, never --continue or interactive --resume. usage/model are read from completed assistant message events; no billing estimates. Spawned children inherit umask077 so native session files are private. Codex argv/output-schema/result-file behavior remains unchanged, with stricter final-result validation applied to both.
