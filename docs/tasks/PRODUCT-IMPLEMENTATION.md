## Running checks

Use Node 26.11.1 and Bun 1.4.1. `bun install --frozen-lockfile`, `bun run verify`, and `bun run test:e2e` are separate gates. The final product browser suite at `40742ce` passed 208/208 across 12 files and 1440, 1024, 390 and 320 pixel Chromium viewports, including failed-source evidence inspection. UI mocks and screenshots do not prove real provider or production behavior.

At `dd989a1`, `bun run verify` passed formatting, typecheck, 394/394 unit tests across 42 files and the production Next build outside the nested sandbox with Chromium sandboxing retained. `bun run test:product:integration` runs the ten configured PostgreSQL suites sequentially. Set `TEST_DATABASE_URL` to a dedicated disposable database ending in `_test`; the suites modify and truncate it. Never use a shared or production database. At `dd989a1` the controlled product integration run passed 244 tests across 27 files: core 150, processing 37, follow-through 15, retention 10, product acceptance 9, operations 5, runtime privacy 2, provisioning 4, import photos 4 and product HTTP 8. The acceptance harness uses a fictional independent oracle, not a live model.

`bun run test:live-provider` is explicitly opt-in: `RUN_LIVE_PROVIDER_CHECK=true`, a configured `OPENAI_API_KEY`, `OPENAI_MODEL`, input and image token limits, pricing and positive monthly budget are required. It runs synthetic English, Spanish and photo-only cases, may incur charges and writes synthetic tenant/budget records to the configured database. Use a private isolated database and approved credentials. The guard was checked without invoking a provider; no live pass is claimed here.

First-organization provisioning is an operator-only CLI for an already verified account; see [provisioning](../provisioning.md). Backup and restore require the correct signing key and the **current deployment-wide signed redaction ledger**, not only a ledger captured with an older backup. Follow [operations](../operations.md) and keep restore targets offline until replay and validation complete.

## Production-image rehearsal

At `dd989a1` for the web image and `40742ce` for the worker image, an isolated local production-container rehearsal passed health/readiness (200), development-route exclusion (404), and sustained worker startup under the unprivileged runtime user. The rehearsal used synthetic accounts and a private PostgreSQL/Mailpit stack. Real HTTP calls completed signup, local email verification, sign-in, owner provisioning and organization selection, source submission/read, manual activity approval, need assignment/acknowledgment and reports showing 60 approved minutes. No external providers were enabled. This check did not exercise live extraction, proposal review, attachment upload, public TLS or a fresh host. Private photo authorization, rollback cleanup and retention have separate controlled PostgreSQL/filesystem integration coverage above.

The worker rehearsal exposed restrictive copied source-directory permissions; `40742ce` makes runtime sources readable/traversable while retaining root ownership and the unprivileged runtime user. Both production images built successfully after this fix.
