# P8-01 — Platform operator console (cross-organization administration)

Status: **implemented, pending independent adversarial review of the diff** (2026-11-09). Decision record: [ADR 0012](../adr/0012-platform-operator-console.md). Wire contract summary: [CONTRACTS](../CONTRACTS.md#platform-operator-surface-additive).

Goal: let an explicitly configured platform operator see every organization and manage its owners, without weakening tenant isolation for any ordinary user and without adding a cross-tenant code path to `/api/product/*`.

## Design after adversarial review

The first draft (email-only allowlist, general role changes, single-phase audit reuse, "no migration" claimed as sufficient) was rejected by an independent adversarial review. The shipped design changed in response:

| Finding                                                                                                                                                                                                                             | Resolution                                                                                                                                                                                                                                                                    |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A verified email is not proof of account ownership: anyone can pre-register an unclaimed address and wait for the real person's verification click, which verifies the squatter's account without rotating its password or sessions | Allowlist entries are `userId:email`; both must match, and the gate is the verified-session check                                                                                                                                                                             |
| Demo addresses and `DEMO_MODE`                                                                                                                                                                                                      | Reserved `.invalid` domains refused; `OPERATOR_ACCOUNTS` refused while `DEMO_MODE=true`                                                                                                                                                                                       |
| `member-role` could promote a volunteer to coordinator                                                                                                                                                                              | The command accepts ownership transitions only (`→owner`, `owner→coordinator`), requires `expectedRole`, and refuses the caller's own membership                                                                                                                              |
| A stale view could overwrite a newer role                                                                                                                                                                                           | `expectedRole` mismatch is `CONFLICT`, never a silent overwrite                                                                                                                                                                                                               |
| Last-owner guard could not hold                                                                                                                                                                                                     | Target membership and every owner row are locked `for update`; a zero-owner result is `CONFLICT`. The remaining cross-path race (tenant self-demotion through Better Auth, unlocked) is pre-existing and needs a database trigger — recorded as a B-owned migration follow-up |
| Operator email in the audit actor would be permanently visible to tenants                                                                                                                                                           | Actor is `{ kind: "operator", userId }` only; the change is still attributed and still rendered in the organization's history                                                                                                                                                 |
| `q` over owner addresses was a harvesting tool                                                                                                                                                                                      | Search matches name and slug only; owner addresses are masked; no endpoint returns an unmasked address                                                                                                                                                                        |
| Unbounded responses                                                                                                                                                                                                                 | 50 organizations per page with keyset cursor, 20 owners per organization, 200 members per detail, integer invitation counts                                                                                                                                                   |
| No rate limits, no step-up                                                                                                                                                                                                          | Per-operator in-memory limits (120 reads / 15 min, 20 writes / hour) and a 30-minute session freshness requirement on mutations                                                                                                                                               |
| Disabled vs. non-operator differed (404 vs. 403)                                                                                                                                                                                    | Every non-operator state is `NOT_FOUND`; outages stay `DEPENDENCY_UNAVAILABLE`                                                                                                                                                                                                |
| Boundary enforced only by convention                                                                                                                                                                                                | `apps/web/lib/operator/boundary.test.ts` fails if the module imports tenant authority                                                                                                                                                                                         |

## Allowed paths changed

- `packages/contracts/src/roles.ts` (new; the role vocabulary moved out of the barrel so `operator.ts` has no initialization cycle), `packages/contracts/src/index.ts`, `packages/contracts/src/operator.ts` + `operator.test.ts`
- `packages/config/src/index.ts`, `packages/config/src/config.test.ts` (`OPERATOR_ACCOUNTS`)
- `apps/web/lib/operator/{accounts,service,store,http,production}.ts` and their tests, `apps/web/app/api/operator/[...path]/route.ts`, `apps/web/app/operator/page.tsx`, `apps/web/components/operator/{console.tsx,console.module.css}`
- `apps/web/components/product/index.tsx` (operator link, rendered only after `operator/session` succeeds)
- `docs/adr/0012-platform-operator-console.md`, `docs/CONTRACTS.md`, this card

No migration, no dependency or lockfile change, no `roleSchema`/`rolePermissions` change, no `/api/product/*` change, no auth-endpoint change.

## Interfaces

- `OperatorDirectory.identify({ userId, email, emailVerified })` — the only authority check.
- `OperatorService` (`list`, `detail`, `createOrganization`, `setMemberRole`) over `OperatorStore`/`OperatorTransaction`; all SQL is isolated in `store.ts` so decisions are testable without a database and every mutation runs inside one transaction.
- HTTP envelope matches the product surface: `{ ok: true, value }` / `{ ok: false, error: { code, message, correlationId, retryable } }`.

## Environment

`OPERATOR_ACCOUNTS` — optional, `userId:email`, comma-separated, ≤20, no `.invalid`, refused with `DEMO_MODE=true`. Absent or blank disables the console (404, no database connection opened).

## Verification

- `apps/web/lib/operator`: 37 unit tests (allowlist binding, masking, transport refusals, origin/freshness/rate limits, dispatch, cursor and query bounds, ownership decisions, last-owner refusal, self-target refusal, stale-view conflict, neutral creation failures, audit payload shape) plus the boundary test.

## Second adversarial review (implementation)

The first implementation was rejected for a functional defect and for unproven database behavior, then fixed:

- the console called `GET /api/operator/organization`, which the transport did not serve, so "Manage owners" was dead — the route is served and a route-coverage test now asserts every console path is answered;
- stale detail responses could render under another organization's heading;
- the console could make the operator an owner (of a new organization) and could change ownership in an organization where the operator is a member — both refused now;
- the keyset cursor now carries the exact `lower(name)` Postgres ordered by, with a 1024-character bound;
- the organization row is read rather than locked, and member rows are locked `order by id for no key update` to avoid lock inversion with the tenant paths and the planned trigger;
- a unique violation on a concurrent slug collision is `CONFLICT`, failures are logged with operation/correlation/code only, `Retry-After` accompanies 429, and the method allowlist is checked after authority resolves;
- the console UI distinguishes denial, rate limiting, outage and a stale session, clears data when authority is lost, and reloads using the submitted search;
- tenant history labels operator rows as "Ownership changed by a platform operator" / "Platform operator".

Real-Postgres evidence (`tests/integration/auth/operator-console.test.ts`, 6 cases, run against a temporary PostgreSQL 18 instance): creation persists organization, settings, membership and audit atomically; two concurrent demotions serialize to one success with one owner and one audit row; a forced audit-insert failure rolls the role change back; last-owner revocation is refused; list and detail expose only masked addresses.

## Unresolved / next integration dependency

1. B-owned migration: `organization.create` audit action value, and the `member` trigger that makes the last-owner invariant hold across every path.
2. Shared provisioning helper so the console and `scripts/provision-organization.ts` cannot drift.
3. Owner notification on ownership change; operator zero-owner recovery; organization rename/delete — out of scope here and tracked in the ADR.
4. No browser/visual acceptance for `/operator` has been run; the page needs the standard 1440/1024/390/320 keyboard and contrast pass before it is claimed as accepted.
