# P7-07 — Edge hardening behind the host Traefik

Status: scoped, not started. Deliberately deferred behind the first deployment: the operator
chose to deploy with the current parity posture (redirect + compression, no hardening) and add
this once the host is live. No implementation is authorized by this card alone.

## Why it exists

The production edge moved from the bundled Caddy to the host Traefik in #5. Both had the same
posture — HTTPS redirect and compression only — so the move changed nothing here. That posture
is not adequate for a public host indefinitely:

- no `Strict-Transport-Security`, so the first request over plain HTTP stays downgradeable
- no baseline security headers (`X-Content-Type-Options`, `Referrer-Policy`,
  `X-Frame-Options`/frame-ancestors, a content-security policy)
- no request body-size limit at the proxy, so oversized uploads reach the application
- no rate limiting on the auth endpoints (`/api/auth/sign-in`, reset request, verification),
  which are the only unauthenticated write paths

## Decisions this card has to settle

1. **Which layer owns each header.** HSTS and frame-ancestors belong to the proxy (they must
   apply to every response, including errors the app never renders). Content-specific headers
   that depend on routes belong to the app. Do not configure both and hope.
2. **HSTS parameters.** `max-age` and whether `includeSubDomains`/`preload` are wanted.
   Preload is effectively irreversible for the domain and must not be set casually.
3. **Whether a shared proxy may own this.** If the VPS Traefik serves other applications, a
   global middleware changes their behaviour too. Either the middleware is per-router
   (`${TRAEFIK_NAME}`-scoped, as `relay-compress` is today) or it is an explicit host contract
   — not an accident.
4. **Limit values.** Body-size cap must be above `ATTACHMENT_MAX_BYTES` and consistent with
   the upload path, or legitimate attachments start failing. Rate-limit keys must be correct
   behind the proxy; note that anything else on the `traefik` network can reach `web:3000`
   directly and supply forged `X-Forwarded-For`, so per-IP limiting is only as trustworthy as
   that boundary.
5. **Failure behaviour.** A rate limit or body cap that fails closed on a proxy hiccup takes
   the whole app down. Decide per rule.

## Acceptance

- Headers and limits verified against a real Traefik in isolated containers, not by reading
  rendered config.
- Sign-in, password reset, verification, attachment upload and the Telegram webhook still work
  with the rules enabled.
- Forged `X-Forwarded-For` and direct shared-network access tested explicitly; state what the
  rate limiter actually keys on.
- Over-limit body and over-rate requests get a defined status, not a 500 or a hang.
- HSTS verified to apply on error responses, not only on 200s.
- No regression to the eleven gates in
  [deployment-preflight.md](../deployment-preflight.md#5-verification).

## Out of scope

Application authorization, tenant isolation, session policy and provider-side protections.
This card hardens the edge only; it does not claim the product is secure because headers exist.
