# P2-07 — Extraction failures: diagnose before deciding

Status: scoped, not started. Opened from a live import on the deployed instance; no
implementation is authorized by this card alone.

**All text quoted below is synthetic**, authored for the import test. No real volunteer,
family or source evidence is reproduced here.

## What actually happened

An import of three synthetic sources produced two clean extractions and one repeated failure.
The failing row read:

> Helped at the food bank on Tuesday evening, about 90 minutes restocking shelves with Luis.

It failed with `VALIDATION` twice, on two different source ids. A direct probe of the same text
through the same provider returned three items with every evidence span matching. So the failure
is neither explained nor reproducible on demand — two failures and one success is not enough to
call it deterministic, and not enough to call it flakiness.

## What we do _not_ know

The cause is **unestablished**. At the time the worker recorded only `reason: VALIDATION`, which
several distinct paths return. Three facts rule out the obvious story:

1. **`receivedAt` never reaches the model.** The request payload carries `sourceId`, `revision`,
   `text`, `timezone`, `occurredAt` and `authorMembershipId` (`packages/ai/src/openai.ts:44-51`).
   With `occurredAt` null the model has no anchor date at all, so "the import timestamp forced
   Tuesday against a Sunday" cannot be the mechanism.
2. **The evidence check contains no date logic.** `verifyProposalEvidence` is defined at
   `packages/ai/src/evidence.ts:49-77` and called at `packages/ai/src/service.ts:253`; it compares
   source identity, revision, span bounds and quote equality. A date can only reach it indirectly,
   by the model quoting a date it computed instead of the phrase in the text.
3. **The fixture provider and the real one do not receive the same input.**
   `packages/ai/src/deterministic.ts:132` anchors on `occurredAt ?? receivedAt`, while the OpenAI
   provider is never given `receivedAt`. Fixture results therefore do not predict live behaviour
   for relative dates, whatever the date question turns out to be.

There is a further signal worth keeping: the _successful_ neighbouring row reported an unresolved
reason claiming "the supplied occurredAt timestamp falls on Sunday in America/New_York" — for a
source whose `occurredAt` is null. The model described context it was never given.

## Candidate causes, none eliminated

- **offset miscount** — correct quote, wrong UTF-16 span, rejected by the span comparison
- **quote drift** — the model paraphrased instead of quoting
- **computed-date quoting** — the model quotes a resolved date that is not in the text
- **model invention** — as in the unresolved reason above
- **proposal-shape rejection** — `packages/ai/src/openai.ts:13` accepts empty `unresolved.field`
  and `reason` strings, while the contract requires `min(1)`
  (`packages/contracts/src/index.ts:256`). That path returns `VALIDATION` under the `proposal`
  key (`packages/ai/src/service.ts:232-250`), not as an evidence position — so the recorded code
  alone cannot even tell us whether this was an evidence failure at all.

## Step 1 — capture, do not guess

The worker now logs bounded detail for these failures: `sourceId`, `revision`, `correlationId`,
the item/evidence positions and the machine codes. The first task is to reproduce the failure
and read the actual codes, then classify it into one of the causes above.

Bound this: if the failure has not reproduced after a stated number of attempts, record that and
proceed to the deterministic work below rather than leaving the card open indefinitely. A live
reproduction is opt-in under the project invariants and is a sample, never proof.

## What this card may need to settle

1. **Which cause is real**, from the captured detail — with the captured codes recorded.
2. **If offsets**: whether the model can be held to exact spans at all, or whether a deterministic
   repair is legitimate (locate the quote in the source and recompute the span rather than
   rejecting).
3. **If dates**: a deterministic rule over `occurredAt` and the organization timezone, expressed
   as a pure post-check. Note that `datePrecision` is `day | unknown`
   (`packages/contracts/src/index.ts:207`), so finer precision is a **contract change** requiring
   coordinator approval and possibly a new schema version.
4. **Whether `receivedAt` should be sent at all.** If the model is expected to reason about
   "Tuesday evening" when `occurredAt` is null, it currently has nothing to reason from. That is a
   prompt-payload decision, and it must be made before the fixture provider is trusted to
   represent it.

## Acceptance

- The failure is reproduced and classified, or a stated attempt bound is exhausted and that
  outcome recorded.
- Any rule added is a pure function over **captured or replayed drafts** — an input/output table
  of draft, timestamps and timezone mapped to accepted, rejected or downgraded. No criterion
  depends on a stochastic model producing a particular answer.
- The fixture provider and the real provider are given the same inputs, so that the
  `occurredAt ?? receivedAt` divergence is closed or explicitly documented.
- A failure names the source, revision, attempt and item/evidence position that failed, and that
  log line has a test.

## Out of scope

Timezone inference, calendar systems, and how the ledger dates approved contributions.
