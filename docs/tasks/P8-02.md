# P8-02 — Operator console hardening: invariants, audit and recovery (design draft)

Status: design draft under adversarial review. Branch `agents/A-operator-console-2` (isolated worktree), based on `6a5392d`.

Follow-up to [P8-01](P8-01.md) and [ADR 0012](../adr/0012-platform-operator-console.md). Closes the migration-gated correctness debt from item 2 and the highest-value parts of the ADR backlog (item 3).

## Scope

### A. Database invariants (one migration, proposed `0016`)

1. `organization_audit_event` action CHECK gains `organization.create`, `organization.update` and `member.add`. P8-01's interim encoding (`member.role` + `organizationCreated`) is replaced.
2. `in_app_notification.need_id` becomes nullable and its type CHECK gains `ownership-changed`, so an ownership change can notify owners without inventing a need.
3. New `platform_audit_event(id, operator_user_id, action, target_organization_id, correlation_id, occurred_at)`: the operator surface's own trail. No FK to `organization` (it must outlive tenant deletion and reads may name no organization), append-only via the existing reject-update trigger function.
4. A `member` trigger pair enforces **at least one owner per organization on every path**:
   - `after update of role on member for each row when (old.role='owner' and new.role<>'owner')`
   - `after delete on member for each row when (old.role='owner')`
   - The function locks the organization row `for update` (returning early when the organization itself is being deleted), then counts remaining owners and raises `23514` when none remain. Lock order stays member→organization, matching the tenant settings path and the operator path, so the trigger does not invert them.

### B. Shared provisioning

`packages/db/src/repositories/provisioning.ts` exports `provisionOrganization(tx, input)` — verified-credential account lookup, advisory lock on the name, case-insensitive name/slug uniqueness, organization insert, owner membership, contract-validated initial settings. Both `scripts/provision-organization.ts` and the operator service call it, so the two paths cannot drift.

### C. Operator surface additions

- `POST operator/organizations` writes `organization.create` (target: organization) plus `member.add` (target: membership) instead of the interim encoding.
- `POST operator/member-add` `{ organizationId, email }` — assign an existing verified credential account as an owner. Covers **zero-owner recovery** and first-owner repair; audit `member.add`; refused for the operator's own account and for an account already in the organization.
- `POST operator/organization-rename` `{ organizationId, name, slug, expectedSlug }` — rename with `expectedSlug` as the optimistic token; audit `organization.update` with `before`/`after`; same separation-of-duties rule as role changes (refused when the operator belongs to that organization).
- Ownership change (grant or revoke) now notifies every current owner through an `ownership-changed` in-app notification written in the same transaction (dedupe key includes the operation id).
- Every operator read (`organizations`, `organization`) and every mutation writes a `platform_audit_event` row. Reads write it **before** the read and fail closed with `DEPENDENCY_UNAVAILABLE` if the trail cannot be recorded; the session probe is not recorded.

### D. UI

Rename form and assign-owner-by-email form in the console; `ownership-changed` rendered in the tenant notifications list.

## Explicitly deferred (recorded in ADR 0012)

Organization deletion/archival, member removal and invitations from the console, email/Telegram delivery of ownership notifications (in-app only for now), shared rate-limit store, and sharing the product connection pool. Each needs its own decision: deletion interacts with evidence and retention, delivery needs the need-based job model reworked, and the others are operational scaling choices.

## Invariants to preserve

- No tenant route gains operator authority; `operator` never becomes a contract role.
- The operator still cannot be made an owner, or manage ownership in an organization they belong to (P8-01 rules).
- Tenant-visible audit rows never contain an operator address; the platform trail is not tenant-readable.
- Every mutation remains one transaction; a failed audit or notification write rolls the change back.
- Existing tenant paths (member invite/role/remove, settings) keep their behavior; only the invariant underneath them becomes unbypassable.

## Acceptance

- Unit: rename conflicts, assign-owner rules, notification fan-out, read-audit ordering and fail-closed behavior, provisioning input validation.
- PostgreSQL: the trigger blocks a tenant-path demotion that would leave zero owners (the P8-01 race), the operator path still cannot leave zero owners, `member.add`/`organization.create`/`organization.update` rows are written, `ownership-changed` notifications land for every owner, `platform_audit_event` records reads and writes, and the CLI and console produce identical organization shapes.
- `bun run verify` plus the integration suites; adversarial review of the diff before acceptance.
